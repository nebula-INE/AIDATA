# Fixed-fixture verification runner

The fixed-fixture runner provides repeatable execution of repository-owned test
suites without evaluating code or commands embedded in dataset records.

## List and run fixtures

```bash
python scripts/verify_fixed_fixtures.py --list
python scripts/verify_fixed_fixtures.py --fixture dataset-validator
python scripts/verify_fixed_fixtures.py \
  --fixture dataset-validator \
  --fixture eval-leakage \
  --timeout 60 \
  --report artifacts/fixed-fixture-report.json
```

Fixture IDs are mapped in `scripts/verify_fixed_fixtures.py` to fixed test-file
patterns. The CLI accepts only registered IDs; it does not accept arbitrary
module names, shell commands, paths, or test selectors. Each suite runs in a
separate subprocess with a timeout, stdin closed, and a reduced environment.
The JSON report records exit status, duration, timeout, command, and captured
output. A timeout is reported as `timeout`, never as a pass.

## Prioritize the human-review queue

Build a CSV of records that most need attention, without copying prompt/target
text into the prioritization report:

```bash
python scripts/prioritize_review_queue.py data/seeds/*.jsonl \
  --review-csv artifacts/review.csv \
  --output artifacts/prioritized-review-queue.csv
```

The review CSV is optional; if omitted, records without a matching completed
review are placed at the top. Held-out `split: eval` records are excluded by
default so they are not mixed into the routine training-data review queue. To
review evaluation records intentionally, pass `--include-eval` explicitly.
Priority levels are workflow heuristics:

- `P0`: review missing or requests revision/retirement, verification failed,
  reviewer missing, or a serious status/evidence inconsistency.
- `P1`: draft/unknown quality status, incomplete evidence metadata, or
  verification not run.
- `P2`: reviewed record with an accepted decision and recorded evidence,
  but not marked verified.
- `P3`: verified record with an accepted decision and recorded passing
  verification evidence.

The queue is sorted by priority and emits IDs, source file, split, task type,
language, status, review decision, and evidence metadata. It rejects malformed
JSONL and duplicate IDs rather than silently omitting them. These priority
levels are not a correctness score. The tool never edits source JSONL or
changes `quality.status`; reviewers must inspect the actual prompt, target,
evidence, and verification scope before changing status.

## Review and evidence coverage report

After a review CSV has been exported and filled in, summarize review progress:

```bash
python scripts/report_review_evidence.py review.csv \
  --fixture-report artifacts/fixed-fixture-report.json \
  --output artifacts/review-evidence-summary.md
```

The fixture report is optional. Without it, the tool reports review decisions,
evidence kinds, and recorded verification-result counts. With it, fixed-fixture
result counts are displayed in a separate section. The tool deliberately does
not infer that a fixture validates any particular dataset record, authenticate
evidence references, or promote `quality.status`. See
`tests/test_report_review_evidence.py` and
`tests/test_prioritize_review_queue.py` for aggregation and prioritization
coverage.

## Link review decisions to evidence

The CSV generated by `scripts/review_dataset.py export` includes these fields:

- `evidence_kind`: `official_source`, `independent_source`,
  `fixed_fixture_report`, `manual_reasoning`, or `not_applicable`.
- `evidence_reference`: a stable URL, repository-relative path, report path,
  fixture/run identifier, or a concise explanation of the manual check.
- `verification_commit`: optional 7- or 40-character hexadecimal commit SHA
  for the code/test version that was checked.
- `verification_result`: `passed`, `failed`, `not_run`, or
  `not_applicable`.

Completed review rows must state an evidence kind, reference, and verification
result. If a fixed-fixture result is marked `passed` or `failed`, the row
must also identify the report and commit SHA. Do not claim that a fixture
verified a dataset answer unless its test scope actually covers that behavior.
For research claims, cite the source that supports the claim, not merely the
search query or a general homepage.

The review validator checks that these fields are present and well-formed; it
does **not** fetch links, confirm that a report exists, authenticate a commit,
or prove that the evidence supports the target. Reviewers must inspect those
references. A recorded `passed` result is evidence only for the stated fixture
scope, not proof of overall answer correctness.

## Important security and quality limits

- This runner executes trusted, repository-owned tests only. Dataset-provided
  source code, `tests` strings, URLs, and commands remain untrusted and are
  never passed to this runner.
- A subprocess and timeout are useful controls, but this implementation is
  **not an OS-level sandbox**. Do not use it to execute arbitrary or unreviewed
  code. For hostile-code testing, use a separately provisioned disposable
  environment with network disabled, no secrets, resource limits, and
  filesystem isolation.
- A successful fixture run means only that the selected repository test suite
  exited successfully in that environment. It does not establish that every
  dataset answer is correct and does not automatically change
  `quality.status` from `draft` to `reviewed` or `verified`.
- Record the commit SHA, runtime, and report when using the results as evidence.
  Review fixture scope and expected behavior before relying on a passing result.

## Current scope

The initial registry covers dataset validation, duplicate auditing, train/eval
leakage checks, coverage reporting, review workflow, and response evaluation.
It is deliberately narrow: add a fixture only when its test file is part of the
repository and its scope is reviewed. Do not derive fixture mappings from
dataset content.
